# 演示脚本

主线约 20 分钟，后期证据段另加 5–8 分钟。每个场景先说"这一段展示什么"，再按表格一步步操作：**点什么 → 屏幕上会看到 → 你说什么**。界面是英文的，按钮名用粗体标出。

---

## 开场前 1 分钟

1. 终端运行 `pnpm start`，等日志出现 "✔ Durable Jev demo is ready"，浏览器自动打开 <http://localhost:4100>。
2. 右上角点 **Reset demo**，所有案例回到初始状态。
3. 左上 **Playback speed** 选第二个图标 ▶▶（中速）。四个图标从左到右是慢、中、快、实时；选实时（⚡）不放动画。

默认是 scripted：Jev 答案按记录回放，调查下一步由可复现的手写策略选择。开场说清楚；只有实际以 live 模式运行时，才能说本次由真实模型判断。

如展示后期证据段，提前运行 `pnpm check`、`pnpm eval:policy-change`、`pnpm eval:investigation`、`pnpm eval:gate-change`。分别按终端最后的 **Report:** 路径，在编辑器打开同目录的 `report.md` 并预览；现场直接切到这三份报告，不等待实验重跑。这些实验用独立数据，不会修改正在演示的订单。

界面四块：左边是案例列表和 agent 列表；中间是当前案例，上面是案例头部，下面是 **Agents / Rule graph / Timeline** 三个视图；右边是当前角色的待办；右上角的角色标签是当前角色和操作人，点它弹出角色菜单，选一个就切换。

**Demo actions** 的按钮会先弹出一个小场景：上半部分 **What happened** 讲发生了什么、谁要怎么办、难点在哪；下半部分 **When you apply it** 讲引擎会怎么处理。照着念就是一段口播："有时候会遇到这种情况……这时引擎会……"，然后点确认，看引擎重新计算。关掉弹窗就不执行。

每个案例头部右上都有一个 ↻ 图标（Reset this case）：只把这个案例恢复到刚收到订单时，从第一条规则重新回放，其他案例不受影响。演砸了就点它。

## 场景 1｜一眼看全局（2 分钟）

**这一段展示：** 5 个 Durable Jev Agent，每个对应一块业务；它们各有数据库，通过消息接收案例资料、交换检查结论。

| # | 点什么 | 屏幕上会看到 | 你说 |
|---|---|---|---|
| 1 | 左侧选 **LOG-004**，中间点 **Agents** | 5 张 agent 卡片和它们之间的箭头 | "每张卡片是一个 agent，负责一块业务：接单协调、货物合规、运输计划、商务、目的地合规。" |
| 2 | 指着卡片上的小标签（Expression / Jev / Human / Combined） | 每个 agent 的规则构成 | "多数规则是配置：公式、语义问题和人工审批步骤。这里只显示一条专用代码规则，不代表整个系统只写了一条代码，也不代表生成和审核成本已经测完。" |
| 3 | 指着箭头上的数字 | 例如商务 → 订单协调 "4" | "箭头表示一个 agent 用到另一个 agent 的结论，数字是用到几条；各自的数据库仍然独立。" |
| 4 | 点 **Cargo assurance** 卡片 | 右侧打开 agent 名片 | "名片上写着它负责什么、要哪些人参与。" |
| 5 | 名片底部展开 **What is a Durable Agent?** | 五条特性 | 挑一句讲："进程挂了，从断的地方接着跑；等人可以等几天。" |
| 6 | 点 **Show its rule graph →** | 只显示货物合规的规则，虚线框是别的 agent 的规则 | "这是它内部的规则流程，虚线是它依赖的外部结论。" |
| 7 | 点视图标签旁的开关 **Only Cargo assurance** | 关掉显示全部规则，再打开又只看这个 agent | "随时可以在单个 agent 和整张规则图之间切换。" |

看不懂颜色时，鼠标移到视图标签右侧的 **Legend** 上，会展开每种颜色和标记的说明，可以直接念。

## 场景 5｜审批不能越权（2 分钟）

**这一段展示：** 审批规则由系统强制：错的角色签不了，同一个人签不了两步，只批一半也放不了行。

**LOG-003：商务主管不能替合规签字**

| # | 点什么 | 屏幕上会看到 | 你说 |
|---|---|---|---|

**LOG-005：两个审批缺一不可，同一个人不能签两步**

| # | 点什么 | 屏幕上会看到 | 你说 |
|---|---|---|---|
| 1 | 选 **LOG-005**，点 **Change the order**（"Reroute via a detour, surcharge 13,000"；改 route 和 quote），点 **Apply change** | 出现两个审批：R34 超授信例外、R35 额外费用 | "改派后超出授信，又多了运费，这是两件独立的事。" |

## 场景 9｜政策门槛变了，已有订单怎么办（3 分钟，可选）

**这一段展示：** NZD 500 → 750，只有严格超过门槛才需要商务审批。当前 UI 没有政策切换按钮；这里展示隔离实验报告，不把 UI 的订单变更按钮说成政策发布。

| # | 操作 | 会看到 | 你说 |
|---|---|---|---|
| 1 | 切到提前打开的政策变更 `report.md`，找到 **parameter-and-rule-version → Full workflow and process recovery** | 两种旧单策略及 NZD 600/800 的结果 | "业务要求改了。关键是旧单继续用旧规则，还是重新按新规则判断。两种都测。" |
| 2 | 指着 `pinned / 600 / false` 和 `re-evaluate / 600 / false` 两行 | 前者仍等审批；后者不再需要审批，旧任务被拒绝 | "同一金额，沿用旧政策要批；按新政策重评就不用批，旧任务也不能再操作。" |
| 3 | 指着 `re-evaluate / 800 / true` | 已经批过仍出现一个进一步审批 | "显式更新规则版本能清理旧任务，但也可能要求重签。这个人工成本必须算进去。" |
| 4 | 向上看 **parameter-only** 的 NZD 600 重评行 | 规则不适用，但旧任务仍打开，迟到审批被接受 | "只改数字还不够。这是已记录的限制，不能据此宣传政策迁移完全自动。" |
| 5 | 看 **Recovery/control problems**；需要细节时打开相邻 `report.json` 的 `recovery` | 不间断、变更前中断、变更后中断的比较 | "48 次完整流程里，32 次经过进程恢复，结果与对照一致，没有重复订舱或放行。这里验证的是业务 SQLite 的连续性。" |

技术 CEO 要看源码时，在仓库终端运行 `git diff baseline-2026-10-24-r2..HEAD -- packages`，说明当前实验复用了原核心，业务包只增加了本地 agent 的关闭方法；再打开 `eval/runner/src/policy-workflow.ts` 看实验接线。编写工具和实验准备也属于成本，要一并看 `git diff baseline-2026-10-24-r2..HEAD -- tools eval/runner`。这里尚未做保险迁移，不能把当前小改动说成保险的迁移成本。

## 场景 10｜调查路径与 Pi 恢复的对照（2 分钟，可选）

**这一段展示：** 相同工具和规则，候选条件变化时走不同路径；对比有无持久化检查点。两种决策策略都是手写的，不作为模型优于固定流程的证据。

| # | 操作 | 会看到 | 你说 |
|---|---|---|---|
| 1 | 切到调查实验的 `report.md`，找到 `first-valid` 条件下、`Restart=false` 的两种策略 | 首个合格就停止检查 1 次；全部检查策略检查 3 次；同一建议 | "我们先把工具与执行边界测清楚。普通确定性代码也可以提前停止，不能把少查两次算成 AI 的优势。" |
| 2 | 指着 `no-valid` 和 `no-offers` 的完整运行行 | `ESCALATED`，没有写入建议 | "没有合格方案就交给人，不编造替代运力。" |
| 3 | 对比同一条件的 `memory / true` 和 `durable / true` | 前者 `CHECKPOINT_LOST`，后者恢复为建议或升级人工 | "业务记录还在，但内存里的调查进度丢了。Pi 持久化保留了完成的步骤，恢复后不重读已完成的资料。" |
| 4 | 在相邻 `report.json` 找一次成功建议的 `wrongRole`、`confirmation`、`repeatedConfirmation` | `ROLE_NOT_ALLOWED`、`ACCEPTED`、`NOT_PROPOSED` | "助手没有直接改订单的权力；计划员确认一次才产生新版本，重复确认被拒绝。" |

如果问“那模型到底能节约多少”：回答“这一步证明执行和恢复机制；真实模型与固定流程的质量、人工投入比较仍待测量”。内存组的预期失败检查通过，不等于内存组恢复成功。

## 场景 11｜增加审批人和证据要求（2 分钟，可选）

**这一段展示：** 不只是改金额，还能改审批链和证据要求；已有任务如何处理，会影响人工成本。仍展示隔离报告，不在 UI 发布政策。

| # | 操作 | 会看到 | 你说 |
|---|---|---|---|
| 1 | 切到 gate-change 的 `report.md`，找 P2 的 `re-evaluate / true` 两行 | `same-version` 再签 1 次，`new-version` 再签 2 次 | "新增质量审核后，保留旧签名和整条链重签，工作量不同；旧链元数据也有不一致，不能一概自动迁移。" |
| 2 | 找 P3 的 `same-version / re-evaluate / false` | `Missing report` 是 `ACCEPTED` | "只更新要求，旧任务仍可能接受不完整证据。新订单测试通过，不能证明旧单迁移安全。" |
| 3 | 对比 P3 的 `new-version / re-evaluate / false` 和 `true` | 都要再提交一次；缺报告是 `MISSING_EVIDENCE` | "版本升级能重新要求证据，但已做过的工作也要再提交，这个成本不能漏算。" |
| 4 | 在相邻 `report.json` 找 `authoring.proposal`，打开该路径的 JSON，展开 `attempts` | 第一次因未改版本被拒，第二次通过；`reviewStatus` 仍是 `pending` | "这段回放人工准备的提案，验证校验、留痕和隔离应用。不是模型独立写对了，更不是成本已经降低。下一步才做独立生成和人工审核计时。" |

技术观众可同时打开该运行目录里 `P2-new-version/policy-v1.md`、`rules.json`，定位 R13；再看 P3 的 R21。指出本轮规则核心没有修改；实验和编写工具的准备成本仍计入。不要现场把提案应用到原始物料目录。
